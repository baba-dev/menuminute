# home-v2 — scroll-assembled dashboard

Status: **the dashboard section is complete** at `/home-v2` (`noindex`, not in the sitemap): the real
sidebar, top bar, hero, KPI row, priorities, outlet health, Service Dispatch, dining floor and
"At your service" panel, the new-order beat, per-chapter captions with links, and a closing call to
action. The rest of the home-v2 page (other sections, navigation, footer) is not built.

## Real components

`dashboard-replica.tsx` renders static, inert replicas using the product's own class names
(`workspace.css`, `workspace-delight.css`), nav model (`src/modules/dashboard/nav-model.ts`), icons,
editorial artwork (`/brand/dashboard/editorial/`) and copy (`getServicePeriodText`, KPI and priority
strings). Values come from `dashboard-build-fixture.ts`: sample data modelled on the public demo
outlet, never a customer's numbers. The body uses the real widget order and `mm-widget-grid`.

- **Virtual screen:** a fixed 1440px (desktop) or 390px (phone) screen scaled to fit with CSS
  `tan(atan2())`, so the real CSS renders at true pixel sizes.
- **Camera:** the real page is taller than a screen, so the stage is a clipped window and a camera
  pans down the page as it builds (`cameraFraction`). The travel is measured from the real layout
  (`ResizeObserver`), never hard-coded.
- **Pinned breakpoints:** the product's CSS re-flows by _viewport_ width (1320, 1280, 1160, 1100,
  900px). `dashboard-build.css` re-asserts the desktop layout in those ranges so the replica looks the
  same on every window size. If the product's responsive rules change, update that block.
- **Phone:** real bottom bar instead of the sidebar, and the real mobile hero. The mobile hero WebPs are
  generated by `scripts/dashboard-media.mjs` (run by `pnpm dev`/`build`, gitignored).
- Counters (KPIs, Dispatch tiles, setup), the setup progress bar, the hero copy, the sidebar links and
  the 12 dining-floor table cards follow scroll and reverse with it. Counters server-render their final
  values, so a no-JS visitor never sees zeros.
- **Camera return:** after the build the camera glides back to the top (`CAMERA_RETURN_START`), so the
  held final frame is the hero and KPIs. The "Live service" chapter points at the bottom (the floor).
- **New-order beat** (`BEATS`): told the way the product tells it, with no invented toast. A quiet
  table card (Table 11) flips to "Order active" (p ≈ 0.86–0.89); as the camera returns, the Service
  Dispatch "Awaiting acceptance" tile goes up by one (≈ 0.95–0.965); once home, the bell badge (and the
  phone Orders badge) count one more (≈ 0.985–0.998). Each is scroll-driven (`--beat`, `data-on`), so it
  reverses on the way up.
- **Captions and links:** the stage is a picture, so the explanatory copy and links live beside it
  (`CHAPTER_CAPTIONS`, one per chapter, shown with the chapter rail). Every link must be an existing
  public page; a test checks it. Copy describes what the replica shows and what the product code does
  (refresh intervals, plan-dependent areas) and makes no availability promises. Reduced-motion and
  no-JS users get every caption as a list. The page ends with a "See it for yourself" CTA to `/demo`
  and `/pricing`.
- The stage is `inert` and `aria-hidden`, so static buttons and links inside the replicas are not
  focusable; hotspots are a later slice.

Dispatch counters, floor order activity and table labels are sample data shaped like the demo outlet
(labels from `src/modules/demo/baseline.ts`); the Dispatch snapshot time is a fixed sample. Known
deviations: the top-bar Help button and the feature-flagged "Shift summary" hero button are
omitted; the till, bell and connection chips are static samples; setup shows 4 of 4 as a sample.

Cost: the route loads `workspace.css`, `workspace-delight.css` and `dashboard-operations.css` (all
class-scoped, no global selectors; the last also carries the availability-dialog styles). Extract a shared stylesheet if bundle size matters.

## Behavior

A tall section pins a stage. Scroll progress `p` (0–1) drives everything through one pure function,
`renderDashboardBuild(stage, p)` in `src/components/marketing/dashboard-build/dashboard-build-timeline.ts`.
Scrolling down assembles the panels; scrolling up takes them apart. There is no separate reverse
animation, so both directions render the same state for the same `p`.

- Native scrolling only: no wheel or touch interception.
- Displayed progress eases toward the scroll target (`dampProgress`) so flicks stay fluid.
- `p` ≥ 0.9 holds the finished dashboard. The stage is `aria-hidden` and has no focusable content yet; hotspots (gated by `INTERACTIVE_AT`) arrive with the feature-link slice.
- Only `transform` and `opacity` are animated.
- Phone (≤ 680px) uses the real mobile layout and a shorter scroll length (400vh vs 500vh).

## Fallbacks

- `prefers-reduced-motion: reduce`: no pin, finished dashboard, chapter rail hidden.
- Scripting disabled: no pin, finished dashboard (the server renders the exploded pose, CSS overrides it).
- In both fallbacks the whole page is shown at its natural height (no window, no camera), scaled to the width with `zoom`.
- `position: sticky` needs no ancestor with `overflow: hidden`; the stage uses `overflow: clip`.

## Marketing fixture

No API calls, auth or tenant data. Every number, time and request is sample data shaped like the public
demo outlet and must not be presented as a customer's data.
