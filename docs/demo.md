# Public demo runbook

Status: **dataset, reset, provisioning, one-click entry, request guard, demo orders, kitchen and
entitlements and Ember limits implemented; the documentation site is planned** (see the plan in the PR description). Read the
[Public demo exception](../AGENTS.md#public-demo-exception) first.

## What exists

- **Dataset:** `src/data/demo/demo-menu.json` (generated by `node scripts/demo/build-demo-menu.mjs`):
  all 236 catalogue dishes in 14 categories. Every field is filled. Values not taken from the 17
  curated culinary profiles are rule-derived **sample data** (`verified:false`). Dishes without an
  approved illustration (`src/data/demo/artwork-gaps.txt`) use the generic plate placeholder
  (`public/icons/category-default.svg`, `imageMode:"none"`) until artwork is delivered.
- **Baseline:** `src/modules/demo/baseline.ts` (menu, 12 tables, outlet text). Public id
  `demo-spice-route-kitchen-v2`; the legacy CI seed (`demo-spice-route-kitchen-v1`) is unchanged.
- **Reset:** migration `0057_demo_outlet_reset.sql` adds `app_private.reset_demo_outlet(jsonb)`.
  It deletes visitor runtime state (orders, kitchen work, service calls, Ember conversations, menu
  imports, overrides, outbox, invitations), republishes the baseline menu at a **monotonic** revision
  and restores the floor plan. Reset takes about 150 ms.
- **Worker job:** runs the reset every 30 minutes when `DEMO_MODE_ENABLED=true`, and
  relies on the 180 s public-menu cache TTL to converge (the worker has no cache credentials). Off by default.

## Entry and guard

- `/demo` shows the entry button only while `DEMO_MODE_ENABLED=true`. `POST /demo/enter` checks the
  Origin, applies a Redis per-source/global limit (fail closed), then signs in the fixed `demo-owner`
  through Better Auth with a password **derived from `AUTH_SECRET`** (`src/modules/demo/credential.ts`).
  No password is published. The session is capped to 2 hours server-side and stale ones are pruned.
- The derived credential is written by `scripts/demo-provision.ts` (needs `AUTH_SECRET`). If the web
  `AUTH_SECRET` is rotated, rerun provisioning.
- `requestActor` enforces an **allowlist** (`src/modules/demo/guard.ts`) for every non-GET request by the
  demo user; unlisted routes answer 403. Better Auth account endpoints (password, email, MFA, delete) and
  device revocation are blocked for the demo session. Sign-in and revocation events and alert emails are
  skipped for the demo user.
- Adding a route that should work in the demo means adding it to the allowlist **and** making sure the
  reset undoes its effects.

## Orders, kitchen and entitlements

- `app_private.provision_demo_ops()` (migration 0058, **migration-owner only**) creates three credential-less
  demo staff, four stations (Tandoor & Grill, Wok & Fry, Curry & Rice, Cold & Sweet), routes every dish by
  category, enables the kitchen, serves the versioned menu (`free_menu_enabled`) and grants `ordering.new`
  and `kitchen.new` for ten years. It deliberately bypasses the Kitchen Pro pilot gate for the demo outlet
  only (ADR 025). `scripts/demo-provision.ts` runs it; re-running is safe.
- Guests can order from `/m/demo-spice-route-kitchen-v2`; orders flow through Orders and the Kitchen display
  exactly as for a real outlet (no payment provider is involved) and are removed by the next reset.
- Each reset re-seeds about 470 orders over 30 days plus a live board (3 pending, 3 accepted, 2 preparing,
  1 ready) from `src/modules/demo/history.ts` (deterministic for a given clock). Live orders progress through
  real status updates, so kitchen work is created by the normal triggers.
- The menu revision is only bumped by a reset when a visitor changed the published menu. The worker cannot
  invalidate the web cache, so after a revert guests may see one "menu changed" conflict for up to 3 minutes.
- Migration 0059 removes the legacy `order_items.variant_id` foreign key. Without it any guest order that
  chose a variant (Half/Full, sizes) failed for **every** tenant (ADR 026).

## Ember (AI assistant) in the demo

- Ember only works if the operator enables it (`AI_ASSISTANT_READ_ONLY_ENABLED`, a verified provider and its
  daily spend cap). The demo never enables actions: `/api/assistant/actions*` is blocked by the guard.
- All visitors share one account, so migration 0060 raises the hard-coded per-user and per-organization daily
  budgets (and their table checks) **only for `demo-owner` / `org-demo-outlet`** (60 conversations, 400 turns,
  800 attempts). Every other tenant keeps 12 / 20 / 80.
- `src/modules/demo/ember-limit.ts` is the real cost ceiling for the demo: 6 turns per source per 10 minutes,
  half that many conversations, `DEMO_AI_DAILY_TURNS` (default 150) turns per UTC day across all visitors, and
  a 280-character prompt cap. Redis failure fails closed. Worst-case daily spend is
  `DEMO_AI_DAILY_TURNS x (two attempts x per-attempt reservation)`; size it against the provider cap.
- **The provider daily spend cap is shared with real tenants.** Set `DEMO_AI_DAILY_TURNS` low enough that the demo
  cannot exhaust it, or give the demo its own provider budget before enabling Ember publicly.
- The UI shows a public-demo notice, demo-specific starter questions and, when the daily allowance is used up,
  clearly labelled sample answers instead of an empty error.
- Pre-launch gate: Ember privacy and retention (issue #230) is still unapproved. Demo conversations are shared
  between visitors and wiped by every reset.

## What a reset never touches

POS ledger (immutable), audit trail, AI spend accounting, identity, entitlements, billing, QR codes,
legacy flat menu tables. The demo outlet therefore does not enable POS or billing.

## Operator steps (production)

1. Verified encrypted off-host backup; ERP HTTP 200 captured before and after (see the runbook).
2. Deploy a reviewed SHA through the normal path so migrations 0057-0059 apply.
3. Provision once (tenant, credential, kitchen, entitlements, history): `ALLOW_DEMO_PROVISION=true AUTH_SECRET=... MIGRATION_DATABASE_URL=... pnpm tsx scripts/demo-provision.ts`.
4. Set `DEMO_MODE_ENABLED=true` in the worker environment and restart the worker.
5. To switch the demo off: set `DEMO_MODE_ENABLED=false` and restart. Existing demo data stays inert.

## Verification

`pnpm test -- tests/demo-reset.test.ts tests/demo-menu.test.ts` (needs the isolated Postgres/Redis
from `pnpm infra:test:up`). `tests/demo-reset.test.ts` fails if a new outlet-scoped table is added
without being reset or explicitly preserved.
