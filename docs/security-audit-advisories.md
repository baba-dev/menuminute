# Reviewed dependency advisories — 7 and 18 November 2026

The frozen dependency audit on PR #330 identified two **moderate** indirect dependencies. Both have upstream fixes but affect toolchain paths, not a demonstrated public MenuMinute endpoint. They remain **unpatched** and must not be described as resolved.

- **esbuild 0.18.20** — [GHSA-67mh-4wv8-2f99](https://github.com/advisories/GHSA-67mh-4wv8-2f99). Included through `drizzle-kit → @esbuild-kit/esm-loader → @esbuild-kit/core-utils`. The issue exposes a locally running esbuild **development server** to cross-origin requests. Production MenuMinute uses the compiled Next.js standalone server, not esbuild's development server. This lowers observed public exposure but does not eliminate the vulnerable dependency. Patch is available at >=0.25.0, requiring review of toolchain compatibility.
- **minimatch 10.2.6** — [GHSA-g3hv-75wg-m249 / CVE-2026-118764](https://github.com/advisories/GHSA-g3hv-75wg-m249). Included through ESLint/TypeScript tooling under `eslint-config-next`. Exploitation requires attacker-controlled glob patterns with vulnerable optimization settings. Current code does not use this package to process public diner patterns. Fixed in >=11.0.1, a major upgrade requiring validation of the linter's transitive compatibility.

**Policy:** `pnpm audit --audit-level high` remains a blocking CI check. The JSON advisory verification permits _only_ the reviewed advisory IDs, versions and paths in this document. Any new moderate finding, different version/path, any high finding other than the single temporary exception below, a critical finding, or an invalid audit report fails CI.

## Temporary HIGH exception — picomatch (recorded 18 November 2026, expires 18 December 2026)

- **picomatch <=4.0.7** — [GHSA-fc5q-39xc-vjpf](https://github.com/advisories/GHSA-fc5q-39xc-vjpf), _ReDoS through single-branch repeated extglobs_ (CWE-1333), severity **high**. The advisory lists the fix as `>=4.0.8`, but **no such release exists on npm**: the newest `picomatch` is 4.0.7 (published 24 Aug 2026) and every older version is also in the vulnerable range, so no upgrade or override can clear it. The finding appeared after the last green `main` CI run (17 Nov 2026) and blocked every pull request and the release path.
- **Why it is accepted for now:** it is reachable only through development tooling — `eslint-config-next` (typescript-eslint, eslint-plugin-import, `@next/eslint-plugin-next`), `vitest` (including the copy `better-auth` declares), `@vitest/coverage-v8` and `@vitejs/plugin-react`. The Next.js standalone production output contains no `picomatch` package (checked on a production build, 18 Nov 2026), so the vulnerable code is not shipped to or executed by the live server. Exploitation needs an attacker-controlled glob pattern with a pathological extglob; the toolchain only evaluates patterns from this repository.
- **How CI enforces it:** `scripts/security/verify-advisory-exceptions.mjs` accepts this one advisory ID only while **all** hold: the date is on or before **2026-12-18** (it then fails closed so the risk must be re-reviewed), every finding is picomatch 4.0.7 or 2.3.2, every dependency path starts at one of the development-tool roots above, and the reported high total equals the accepted advisory. A critical finding or any other high advisory still fails. The native `pnpm audit --audit-level high --ignore GHSA-fc5q-39xc-vjpf` step runs **after** the JSON verification because `pnpm audit --ignore` persists the ID into `pnpm-workspace.yaml`, which would hide it from the verifier.
- **Removal:** when `picomatch@>=4.0.8` is published, update the lockfile (for example `pnpm update picomatch --depth Infinity`, adding the exact version to `minimumReleaseAgeExclude` if the release-age policy blocks a brand-new release), then delete the `temporaryHighExceptions` entry and the `--ignore` flag. This is recorded risk acceptance for a bounded period, not a fix and not proof of zero vulnerabilities.

**Remediation:** Upgrade each transitive toolchain through compatible maintained parent releases, or use a thoroughly tested override with exact new lockfile integrity hashes. Do not force major transitive overrides blindly on the shared production build. Full ARM64 frozen installs, lint, migration checks and browser tests must pass after each proposed upgrade. Remove a CI exception as soon as its vulnerable copy is eliminated. This is recorded risk acceptance for the review interval, not a blanket exemption or proof of zero vulnerabilities.
